# Trip Service — Лабораторная работа 1

Сервис управления поездками (Trip Service), реализованный на Go в рамках курса по микросервисам.

---

## 1. Запуск сервиса

### Требования
- Go 1.24+
- Запущенный кластер и окружение (`tripgoctl`) или локальный PostgreSQL

### Команды
```bash
# 1. Запуск окружения (если используется tripgoctl)
tripgoctl cluster start
tripgoctl environment start

# 2. Накатить миграции
make migrate

# 3. Запустить сервис локально
make run

# 4. Прогнать тесты с проверкой гонок
make test

# 5. Перегенерировать OpenAPI клиент/сервер
make generate
```

## 3. Архитектурные решения

### 3.1. Запрет двух активных поездок на одного водителя
- **Проблема**: Если проверять занятость водителя через `SELECT` перед `INSERT` в Go-коде, то при одновременных параллельных запросах возникнет состояние гонки (Race Condition): оба запроса увидят, что активных поездок нет, и оба выполнят `INSERT`.
- **Решение**: Правило закреплено на уровне СУБД с помощью **частичного уникального индекса**:
  ```sql
  CREATE UNIQUE INDEX trips_driver_active_idx ON trips (driver_id) WHERE status = 'active';
  ```
  Индекс индексирует строку водителя только в том случае, если `status = 'active'`. При попытке создать вторую активную поездку PostgreSQL возвращает ошибку нарушения уникальности с кодом `23505`. Репозиторий перехватывает `23505` и транслирует её в доменную ошибку `ErrDriverBusy`, которая преобразуется в ответ `409 Conflict` (`code: driver_busy`).

### 3.2. Менеджер транзакций (`TxManager`)
- Бизнес-логика (`TripService`) не зависит от `pgx` и структуры БД. Менеджер транзакций предоставляет интерфейс:
  ```go
  type TxManager interface {
      Do(ctx context.Context, fn func(ctx context.Context) error) error
  }
  ```
- **Контекст**: `TxManager.Do` открывает транзакцию и помещает её в `context.Context` под закрытым типом ключа (`txKey{}`).
- **Вложенность**: Если внутри `Do` вызывается другой `Do`, менеджер проверяет наличие транзакции в контексте и переиспользует её без открытия второй.
- **Откат и паника**:
  - При ошибке внутри `fn` вызывается `tx.Rollback(ctx)`.
  - При панике внутри `fn` срабатывает `recover()`, транзакция откатывается через `tx.Rollback(ctx)`, а паника пробрасывается дальше (`panic(p)`).
  - При успешном завершении `fn` вызывается `tx.Commit(ctx)`.
- **Исполнитель запросов (`Executor`)**: Метод `txmanager.GetExecutor(ctx, pool)` проверяет контекст. Если в контексте есть транзакция — запросы репозитория выполняются через неё. Если транзакции нет — напрямую через `pgxpool.Pool`.

### 3.3. Выбор уровня изоляции транзакций
- По умолчанию выбран **`Read Committed`** (стандартный для PostgreSQL).
- **Обоснование**:
  1. `Read Committed` обеспечивает высокую производительность и минимальные блокировки при конкурентной нагрузке.
  2. Риск фантомных вставок двух активных поездок полностью нивелируется частичным уникальным индексом на стороне PostgreSQL.
  3. Риск состояния гонки при завершении поездки предотвращается атомарным запросом `UPDATE ... WHERE id = $1 AND status = 'active'`.
  4. Более строгие уровни изоляции (`Repeatable Read`, `Serializable`) избыточны для нашего сценария и приводили бы к частым ошибкам сериализации (`40001 serialization_failure`), требующим логики ретраев.

### 3.4. Безопасное завершение поездки (`FinishTrip`)
- Завершение поездки выполняется одним атомарным SQL-запросом:
  ```sql
  UPDATE trips
  SET status = 'completed', finished_at = $1, updated_at = now()
  WHERE id = $2 AND status = 'active'
  RETURNING ...;
  ```
- Если два клиента одновременно вызовут `/finish`, ровно один запрос переведет статус из `active` в `completed` и вернет `200 OK`. Второй запрос не найдет строк с `status = 'active'` и вернет 0 затронутых строк.
- Для различия кодов ошибок при нуле затронутых строк выполняется чтение:
  - Если поездки с таким ID вообще нет в БД $\rightarrow$ отдается `404 Not Found` (`code: trip_not_found`).
  - Если поездка найдена, но уже имеет статус `completed` $\rightarrow$ отдается `409 Conflict` (`code: trip_completed`).

### 3.5. Разделение `/health` и `/ready`
- **/health (Liveness Probe)**: Проверяет, что процесс жив и способен отвечать по HTTP. **Не ходит в БД**. Если база временно недоступна, liveness probe должна оставаться успешной, иначе оркестратор (Kubernetes) начнет циклически перезагружать под, усугубляя аварию каскадным перезапуском.
- **/ready (Readiness Probe)**: Проверяет готовность сервиса обрабатывать пользовательский трафик, выполняя `pool.Ping()`. При недоступности БД отдает `503 Service Unavailable`, сообщая балансировщику временно снять трафик с инстанса до восстановления связи.
